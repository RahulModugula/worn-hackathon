## 3. Glasses state machine

`G1 Idle/Scan` → `G2 Scanning` → `G3 Scan Failed` | `G4 Meds Card` → `G5 Med Logged` | `G6 PRN` | `G7 Wound prompt` → `H3 capture` → `G8 Wound Assessment` → `G9 Phone Notice`; plus `Vitals` and `Critical Allergy Alert`.

Auto-fade: **G4 and G8 never fade while a patient is loaded.** G5 3s · G6 10s · G9 6s · voice toast 3s. **Critical Allergy Alert never fades; requires spoken/typed "acknowledge".**

Scanner runs only on G1/G2/G3 (4 FPS = 250ms). Off those screens (and except H3, which needs a frame) the camera pump stops and the video track is disabled; it resumes on return to G1-G3 (temple thermals, battery). Crop = center 480×480 of a 1280×720 frame, so edge-of-view wristbands never decode. Dwell: first valid read G1→G2; 3 matching reads within 1.2s → lock patient → G4 + `SET_ACTIVE_PATIENT`. Unknown code or 5s in G2 → G3.

Voice triggers (patient loaded, 60s per-patient per-trigger cooldown): pain regex → G6 if patient has PRN; wound regex → G7 if patient has wound. `"room 12"` / `"room 14"` loads a patient on glasses only (phone chart unchanged).

## 4. Sync contract

- Server in-memory `sessions: Map<id, SessionState>`; `applyAction` is synchronous (single-threaded Node ⇒ FWW is race-free).
- Session `demo` by default, `?session=<id>` overrides. WS `/ws?session=<id>&device=<glasses|phone|director>`.
- Every action carries a UUID `clientEventId`; replay of a seen id returns the original result (idempotent).
- `LOG_MED` on an already-`given` med → `{ok:false, conflict:true, message:"Already given {time} via {via}"}` + authoritative state.
- `UNDO_LAST_MED`: either device, ≤10,000ms after server `acceptedAtMs`; reverts to `due` on both.
- Offline: client persists last `SessionState` + `outbox[]` in `localStorage`; `Force Offline` toggle in Director Drawer and desktop debug bar. On reconnect, flush outbox in order and adopt server FWW results.
- `RESET_SESSION` clears shift, clock, activePatientId, medStatus, woundCaptures, glassesNotice, events, lastMedLog on both devices in <500ms and clears local outbox.
- **Acknowledgements:** the server answers the dispatching client with `{t:'result', clientEventId, result}` for EVERY action (ok, conflict or failure; a validation error carries the `clientEventId` too). `useSession` exposes `lastResult` and an `onResult` callback; glasses and phone toast refused actions live (`Already given ...`, `Too late to undo`).
- **Presence:** `{t:'presence', presence:{glasses,phone,director}}` (socket counts for the session) is sent on every connect and disconnect. The phone `Glasses connected` badge reads it. The stage mirror connects as `director`, so it never counts as glasses.
- **Identity and director capability:** the server derives `device` from the socket (`device=` query), never from the message body. `RESET_SESSION`, `SET_CLOCK_OFFSET`, every `SIM_*` and a `START_SHIFT` with `baseMin` need director capability (`device=director` or `director=1` on the connection; with env `DIRECTOR_KEY` set, also a matching `key`), else the result is `{ok:false, message:"Director only"}`. The nurse's plain `START_SHIFT` is allowed from the phone. The idempotency cache is keyed `device:clientEventId` per session. Sessions are capped at 50 (oldest idle evicted); `/ws/stt` at 4 concurrent sockets.
- **Validation bounds:** `START_SHIFT.baseMin` is an integer 0..1439, `SET_CLOCK_OFFSET` is finite within +-1440, notice text is a string of at most 200 characters, `SET_GLASSES_VIEW` and `payload` are size bounded, and non-finite numbers are rejected.
- **Photo:** the glasses resize to 512 px wide JPEG at quality 0.65; the client waits at most 4 s for an assessment, then shows the sample result.
- **Heartbeat and wake:** client `{t:'ping'}` every 10s, server `{t:'pong'}`; no traffic within 5s of a ping means the socket is dead (actions queue in the outbox, reconnect at once). `visibilitychange` (visible), `pageshow` and `online` also force an immediate reconnect (iPhone sleep). The server also pings every 15s and terminates a socket that misses two pongs, so presence is honest.
- **Sync health and chaos (protocol):**
  - Client ping: `{t:'ping', n, v, q, rtt?, offlineMs?}`: `n` a sequence number, `v` the `state.version` the client holds, `q` its outbox length, `rtt` its last measured round trip (ms), `offlineMs` (once per outage, on the first ping after a reconnect, sent BEFORE the outbox flush so the queue depth is visible) how long it was away. The server answers `{t:'pong', n}` and the client times the round trip (`rttMs` in its snapshot). A newer state version is also reported by a debounced (150 ms) extra ping, so the Director sees convergence in real time. Every field is optional and bounded server side (`shared/stats.ts parsePing`; out-of-range values are dropped, the ping is still answered).
  - Director `stats` frame: `{t:'stats', peers: PeerStats[], serverVersion}` sent ONLY to director sockets of the session (the stage mirror connects as director), on change only and at most 2 per second (leading plus one trailing frame). `PeerStats {device, instance?, v: number|null, q, rttMs: number|null, lastSeenMs, offlineSince: number|null, lastOfflineMs: number|null}`; a dropped peer that had an `instance` stays listed with `offlineSince` set for 60 s, and reconnecting with the same instance replaces it (its `lastOfflineMs` is the outage the client reported). `shared/stats.ts convergence(peers, serverVersion)` returns `{status:'converged'|'behind'|'idle', behind, offline}`: behind = a connected peer whose reported `v` differs from `serverVersion` (unknown `v` and offline peers are not counted as behind).
  - `SIM_CHAOS_DROP` (director) payload `{ms: integer 3000..15000, thenDone?: boolean}`: the GLASSES handle it in their event loop (client timers only, no server timer): go offline now (`setForceOffline(true)`), with `thenDone` run the local `done` 1.5 s later (it queues in the outbox: `Queued · offline`), and go online again after `ms`; the outbox then flushes and first-write-wins applies, so the med is given exactly once. A second drop restarts the timers; an out-of-range payload does nothing. Proven end to end in `server/offlineFlush.test.ts`.
  - The glasses push `SET_GLASSES_VIEW` only while online, so the stage mirror (`?mirror=1`) would freeze at the last view when they drop: when the session `presence.glasses === 0` and a view was ever pushed, the mirror renders that view with the connection item `Not linked` (no pushed view, the display-only flow, is unchanged).
- **Event cursor:** every recorded event has a monotonic `seq`; `eventSeq` is the newest and survives `RESET_SESSION`. A client acts on each event once (cursor = last seq acted on). A fresh page load adopts the current `eventSeq` as its cursor after its first `state` frame and replays nothing. A reconnect within the same page session keeps its cursor, so a director command sent while the glasses were offline still runs once (a RESET or a lower `eventSeq` re-baselines).
- **Wound lifecycle (server-authoritative, `woundCaptures[]`):** `WoundCapture {captureId, patientId, status: captured|pending_review|saved|sent, photoUploadFailed, finding, comparison, draftNote, source: glasses|director, assessmentSource?: gemini|fallback|unavailable (G8 and P3 label it "AI result" or, for a fallback, "Photo only" with the non-clinical text "No AI review - see phone" (the server records the real source per captureId and overrides client claims); `unavailable` = no photo, text `Assessment unavailable: no photo captured`, no finding, cannot be sent), capturedAtMs, sentTo?, reply?}`. Actions: `WOUND_CAPTURED` (glasses H3 result with the assessment; with `photoUploadFailed:true` and no assessment when the upload fails; upsert by `captureId`), `WOUND_RETRY_UPLOAD` (same `captureId`, clears the flag), `WOUND_SAVE`, `WOUND_SEND` (marks `sent`, sets `sentTo`, glasses notice `Sent to {attending}`; refused with `No assessment to send` when `assessmentSource` is `unavailable`). The glasses G8 "send" dispatches `WOUND_SEND` with the `captureId` and shows the confirmation only after the server ack (hint `Sending to {attending}…` until then), `DR_REPLY` (reply on the capture plus a G9 notice, `kind:'dr_reply'`). Idempotent by `clientEventId`; first-write-wins by `captureId`: a second save/send returns `{ok:false, conflict:true, message:"Already sent to {attending}"}` and changes nothing. The 5s simulated doctor reply is a timer in `server/index.ts` (never inside `applyAction`), cancelled by `RESET_SESSION`; `SIM_DR_REPLY` fires it immediately. `GET /api/wound-photo/:captureId` serves the uploaded JPEG for P3.
- **Dressing documentation (nurse-entered, `docs/HYDROGEL-RESEARCH.md`):** `WoundCapture.dressing?: {type: hydrogel|hydrocolloid|foam|alginate|film|gauze|other|none, changedAtMin?, intervalHours?: 24|48|72|null, nextDueMin: number|null, enteredBy, atMs}`. Action `WOUND_SET_DRESSING {captureId, dressingType, changedAtMin?, intervalHours?}`: `changedAtMin` is an integer 0..1439 on the demo clock, `intervalHours` must be one of the nurse-picked presets 24, 48, 72 or `null` (= per protocol, no next-due time), both required unless the type is `none`. The server only adds (`nextDueMin = (changedAtMin + intervalHours*60) mod 1440`); it never chooses an interval, and no interval is a clinical recommendation. Semantics follow WOUND_SAVE/SEND: idempotent by `clientEventId`, editable while the capture is `captured` or `pending_review`, frozen once `saved` (`Already saved`) or `sent` (`Already sent to {attending}`), `No wound capture` for an unknown id, cleared with the capture by `RESET_SESSION`, and kept when a later `WOUND_CAPTURED` upserts the capture. It enters the feed as `wound_dressing` with the chain `Documented by nurse`. P3 shows a Dressing card (type pick list, last changed, interval presets, `Documented by nurse`) and adds one `Dressing (documented by nurse): ...` line to the draft on Save and Send. G7 reads the newest documented dressing per patient from session data. Director `SIM_DRESSING_PRESET` ("Demo: Set Dressing") documents Hydrogel, changed at the demo clock, 24 h on the newest unsaved capture (`Capture a wound photo first` when there is none); it is a demo convenience, not a recommendation. All wound text is a documentation aid and a draft for clinician review, never a diagnosis.
- **Wave 2A contract:**
  - `LOG_MED.earlyConfirmed?: boolean`, `LOG_MED.scanLocked?: boolean`. A med whose `dueAt` is more than 30 demo minutes away is refused `{ok:false, needsConfirm:true, message:"Not due until {time}"}` unless `earlyConfirmed:true`. `scanLocked` (set by the glasses when a real wristband scan locked this patient) adds `Wristband matched` to the feed chain.
  - `TELEMETRY_SAMPLE {metric: scanToCardMs|doneToAckMs|assessMs|outboxQueuedMs, ms}` (`outboxQueuedMs`: how long an action sat in the glasses' offline outbox before it was flushed, one sample per flushed action) from glasses/phone: last 20 per metric in `SessionState.telemetry`, cleared by `RESET_SESSION`, never an event. `GET /api/telemetry?session=demo` returns `{session, telemetry}`; `node scripts/export-telemetry.mjs [--url http://host:3001] [--session demo]` prints the markdown table for `docs/decisions/kill-gate.md`. `/glasses?debug=1` shows p50 / max and the WebView Chrome version.
  - `UNDO_LAST_MED` after 10 s returns `Too late to undo`.
  - Bus vs feed: `events[]` is the command bus the glasses replay (it keeps `SIM_*`; `SET_GLASSES_VIEW` and `TELEMETRY_SAMPLE` are no longer recorded). `SessionState.feed[]` (last 60) is the activity feed for P4: only med and wound events, each `{seq, atMs, kind: med_given|med_undone|wound_captured|wound_saved|wound_sent|wound_dressing|dr_reply, device, patientId, patientName, room, medName, timeLabel, chain[]}` with a verification chain such as `Wristband matched`, `Nurse confirmed via voice|tap|phone`, `Server accepted`.
  - Allergy: meds may carry `allergyClasses` (additive); `shared/allergy.ts checkAllergy(patient, med)` matches them to the chart allergies. The glasses show Critical Allergy (filled diamond + `Allergy`, the drug as hero, `Chart lists Penicillin allergy`, `Say "acknowledge"`) for a due or newly added conflicting order; it never blocks logging. `SIM_ADD_CONFLICT_ORDER` (director) injects `Amoxicillin 250 mg PO` (class penicillin) for P-1012 into `SessionState.extraOrders` so the alert is real.
  - Heard/listening: `Listening` in the strip only while the mic is genuinely live (the voice engine emits `{type:'mic', live}`: tier 1 after `getUserMedia` resolved, tier 2 on the recognizer's `onaudiostart`, never at tier 3 or on a mere request); `Heard: {command}` for 1.5 s after a recognized command; `Try "done", "vitals", or "close"` on a miss.
  - The glasses adopt a patient set elsewhere (the phone scanned): a change of `activePatientId` loads that card (assignment check applies) with no dispatch back; the mirror shows it when no glasses push a view.
- **Allergy safety (protocol):** acknowledging an alert is not consent to give the drug. `LOG_MED` on a med where `checkAllergy` hits is refused `{ok:false, needsConfirm:true, message:"Chart lists {allergy} allergy"}` unless the action carries `allergyConfirmed:true` (boolean, validateAction bound; the glasses never send it, the phone sends it only from its confirm dialog, which reuses the early-dose sheet). On the glasses an acknowledged conflicting order sorts LAST in the due list, so "done" logs the next real med; "done" on the conflicting med shows `Allergy · confirm on phone` and dispatches nothing. `ALLERGY_ACK {patientId, medKey, via?: 'voice'|'tap'}` (glasses dispatch it on acknowledge) appends `{key:"{patientId}:{medKey}", atMs, label, device, via}` to `SessionState.allergyAcks[]` (cap 20; the med must exist and conflict; idempotent: a second ack returns `{ok:false, conflict:true, message:"Already acknowledged {time}"}`), adds a feed entry `kind:'allergy_ack'` with chain `['New order (simulated prescriber)' (or 'Order on chart'), 'Chart lists {allergy} allergy', 'Shown on glasses', 'Acknowledged via voice|tap', 'Server accepted']`, and `RESET_SESSION` deletes the key. The glasses seed their local `ackAlerts` from `allergyAcks`, so another wearer is not re-alerted. A confirmed give adds `Allergy override confirmed` to the med feed chain.
- **Handoff (I-PASS, deterministic, no LLM):** `data/patients.json` carries `handoffNurses [{id:'N-01',name:'Priya S.'},{id:'N-02',name:'Marcus T.'}]` (synthetic). `shared/handoff.ts buildHandoff(state, patient, extraOrders, nowMin, severity?) -> HandoffItem[]` (`{section:'I'|'P'|'A'|'S', text, critical}`): **I** `Illness severity: Not stated` unless the nurse chose Stable, Watch or Unstable (never computed); **P** name and room, allergies, attending; **A** ungiven meds due in the next 4 h (or overdue; an allergy-conflicting order is flagged), PRN eligible time, dressing due (`woundCaptures[].dressing` when present, else the chart interval); **S** from `state.feed` for this patient (meds given with time and via, an undo cancels the give, allergy acknowledgements, wound sent and doctor reply). The final S (synthesis) is the receiver's read-back. **Critical** items: every allergy item and every med given in the last 4 h.
  - `SessionState.handoffs?: HandoffPacket[]` (newest last, cap 10; `RESET_SESSION` deletes the key). `HandoffPacket {handoffId, patientId, fromNurseId, toNurseId, severity?, items, status:'offered'|'accepted', offeredByInstance, offeredVia:'glasses'|'phone', createdLabel, readBack:number[], acceptedAtMs?, acceptedLabel?, acceptedByInstance?}`.
  - **Instance:** `Base.instance?` is set by the SERVER only: `index.ts` reads `instance=` from the WS connect query (uuid-shaped: hex and dashes, 8 to 64 chars; anything else means no instance) and stamps it next to `device`; an `instance` in a frame body is dropped by `validateAction`. Clients get an id per browser tab from `getInstanceId()` (hud-kit `useSession.ts`, sessionStorage) and append `&instance=` to the socket URL (the phone and glasses already do). A missing instance fails closed for readback and accept.
  - `HANDOFF_OFFER {handoffId, patientId, toNurseId, severity?}` (handoffId and ids match `[A-Za-z0-9_-]{1,64}`; phone, glasses): refused `Not on your list` (assignment), `Unknown patient`, `Unknown nurse`, `Pick the receiving nurse` (to yourself); conflict `Already offered` (same handoffId) or `Handoff already offered` (an open offer for the same patient and nurse). Builds the packet, sets `glassesNotice {text:'Handoff sent · {name}', kind:'handoff'}`, feed `handoff_offered` (`label:'{from} to {to}'`, chain `['Built from shift log','Offered from glasses'|'Offered from phone','Server accepted']`; `offeredVia` is `glasses` only when the action's device is glasses, so a director-phone offer is honestly `phone`).
  - `HANDOFF_READBACK {handoffId, index}`: critical items only (`Not a critical item`, `No such item`), from an instance that is not the offering one (`Read back on the receiving nurse's device`), idempotent (a second read-back is `ok` and changes nothing), after acceptance a conflict.
  - `HANDOFF_ACCEPT {handoffId}`: refused `Read back {n} critical items first` while any critical index is unread (n = how many are left), refused `Accept on the receiving nurse's device` when the instance is missing or equals `offeredByInstance`; second accept is first-write-wins `{ok:false, conflict:true, message:'Already accepted by Marcus T. {time}'}`. Success sets `glassesNotice {text:'Handoff accepted · Marcus T.', kind:'handoff'}` and feed `handoff_accepted`, chain `['Built from shift log','Offered from glasses'|'Offered from phone','{n} critical items read back','Accepted on another device','Server accepted']`. Invariant (fuzzed in `server/handoff.test.ts`): accepted implies every critical index is in `readBack` and `acceptedByInstance` differs from `offeredByInstance`.
  - Director: `SIM_HANDOFF_OFFER` payload `{patientId?, toNurseId?, severity?}` is director-only; like every `SIM_*` it is recorded on the bus with its payload as event `detail`, and the GLASSES then dispatch `HANDOFF_OFFER` (so the verification chain credits the glasses; a director-phone action is stamped `director`). If no patient is loaded the glasses load Rm 12 first; `toNurseId` defaults to the first roster nurse who is not the signed-in one. The voice intent `handoff` (`hand off`, `handoff`, `hand over`, `handover`; at most 6 words, negations and questions never fire, final transcripts only, 60 s cooldown per patient) dispatches the same offer.
- **Assignment:** the server refuses `SET_ACTIVE_PATIENT` for an id not in `nurse.assignedPatientIds` (`data/patients.json`) with `Not on your list`.
- `SIM_FAIL_PHOTO_UPLOAD` toggles `photoUploadShouldFail` (true, false, true...); uploads fail while it is on; the Director button shows `Toggle Photo Fail: ON|OFF`. `SIM_CAPTURE_WOUND` makes the glasses run a real capture with `/data/wound-fallback.jpg` (loads Rm 12 first if no patient), so the director reaches G8 without a tap.

## 5. Demo clock

Shift start sets the clock to **1:42 PM (822 min)**, running 1:1 with real time. A med is actionable ("Due now") when `dueMinutes − nowMinutes ≤ 30`. At start: Metformin 2:00 PM = 18 min (due now); Aspirin 2:10 PM = 28 min (due now); Atorvastatin 2:30 PM = 48 min (NOT due); Oxycodone PRN 10:15 AM + 4h = 2:15 PM = 33 min.

## 6. Spec correction (found while writing issues)

The brief gives James Carter two `due` meds "to test `next` cycling", but under the ≤30-min rule only Aspirin is due at 1:42 PM; Atorvastatin (2:30 PM) becomes due at 2:00 PM, 18 real minutes later. **Fix: add a Director `[Clock +30m]` control (`SIM_CLOCK_PLUS_30` → adds 30 to a `clockOffsetMin` in session state).** Seed data stays exactly as briefed. `RESET_SESSION` zeroes the offset.

## 7. Acceptance criteria (14)

Numbers 4, 10, 12, 13, 14 match the original brief; the rest are numbered by us.

1. **Start Shift** on phone starts the 1:42 PM demo clock; glasses and phone both show it.
2. **Scan → patient:** a band at 5cm in center view goes G1→G2→G4 in ≤2s and phone P2 auto-opens that patient.
3. **Meds card content:** Maria shows Metformin due now, the Penicillin allergy diamond visible on the action line, and `Due now · Gluc 182 (11:00a)`.
